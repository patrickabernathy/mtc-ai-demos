Give the site a phone view

The Daily Grind has a one-page site, and it was designed on a laptop — only on a laptop. Every class in it describes the wide screen. Nobody ever decided what a phone should get. Tonight you design and build the phone view, one section at a time, without losing the laptop view you already have.

1. Run it, laptop first

npm install
npm run dev

Open http://localhost:3000 in a normal, wide browser window. That's the design: a header with a row of links, a hero with the text beside a photo, three feature cards across, hours next to the location, a signup form, and a footer. Keep this look in your head — by the end of the night it should still look exactly like this on a laptop.

Now open DevTools, turn on the device toolbar (Ctrl+Shift+M, Cmd+Shift+M on a Mac), and set the width to 375. That's what a phone gets today: the laptop layout, squeezed. Three cards side by side in a space meant for one. Nothing is wrong with the code — the phone version was simply never written.

2. The one rule, and the one move

Same rule as class: a class with no prefix applies on every screen, phones included. md: means "from 768px up." So the phone version is the default, and the laptop version is the upgrade.

That turns tonight into one move, repeated. Find a class that only makes sense on a wide screen, put md: in front of it, and write what the phone gets with no prefix:

grid-cols-3     →  grid-cols-1 md:grid-cols-3
flex (a row)    →  flex flex-col md:flex-row
w-1/2           →  w-full md:w-1/2
text-6xl        →  text-4xl md:text-6xl

Here's the phone design, decided for you, so tonight is about building it:

SectionLaptop (already built)Phone (you add this)

Hours / Find the cartSide by sideHours on top, location under it

AI hint — before you start. If "phone first" still feels backwards, ask:

"In Tailwind, why does a class with no prefix apply on a phone, and why is md: a minimum width instead of a maximum? What would go wrong if I wrote the laptop version with no prefix and tried to fix the phone with a prefix?"

3. Features: one card per row

Required. The warm-up, and the exact move from class. In components/Features.tsx:

grid grid-cols-1 md:grid-cols-3 gap-4 md:gap-8

A 32px gap between cards stacked on a phone is a lot of empty screen, so the gap gets a phone version too.

Stop and check — do this after every section. Look at 375 (one card per row), then drag the width up past 768 (three across again), then a full laptop width. If the laptop view changed, a class lost its md: somewhere.

4. Hours and location: stacked

Required. In components/VisitUs.tsx, the <section> is a two-column grid. Give the phone one column and keep two from md up. Shrink the gap-12 on the phone while you're there.

5. Hero: text above the photo

Required. components/Hero.tsx has the most to change. Work through it one class at a time:

  • The <section> is a flex row. On a phone it should be a column: flex flex-col md:flex-row. items-center only makes sense for a row, so it becomes md:items-center.
  • Both halves say w-1/2. Half of a phone is too narrow to read. w-full md:w-1/2 on both.
  • text-6xl puts one word per line on a phone, and "neighbourhood" doesn't fit at all. Pick a phone size — text-4xl is a good start — and keep md:text-6xl.
  • The photo box is h-80 (320px). Stacked under the text on a phone, that's most of a screen of yellow. Give the phone something shorter, like h-48.

Every section has px-8. Thirty-two pixels of padding on each side is fine on a laptop and eats a sixth of a phone screen. As you go through each section, make it px-4 md:px-8. Same move, smallest possible version of it.

6. Signup: full width

Required. In components/Signup.tsx, the form is w-96 — exactly 384 pixels, on purpose, because a sign-up form stretched across a whole laptop looks silly. But 384 pixels is wider than a 375-pixel phone, so on a phone the page can be dragged sideways.

On a phone the form should fill the width, with the input above the button:

flex flex-col md:flex-row gap-2 w-full md:w-96 mx-auto

Stop and check. At 375, try to drag the page sideways, or look for a horizontal scrollbar at the bottom. The signup form shouldn't cause one anymore. (The header still does — that's step 8.)

7. Footer: stacked

Required. components/Footer.tsx is a flex row with items-center and justify-between. On a phone, stack the three lines (flex-col plus a small gap-2), and move the row, the centring, and the justify-between behind md:.

8. Header: a Menu button

Required. The biggest change, because on a phone the header isn't just rearranged — part of it is swapped for something else. Four links and an Order button don't fit next to the logo on a phone, so the phone gets a Menu button instead, and the links drop down underneath when you tap it.

Open or closed is state, so components/SiteHeader.tsx needs "use client"; at the top and a useState, same as the cart back in week 6. Here's the shape; fill in the classes and the links:

"use client";

import { useState } from "react";

const links = ["Our coffee", "Locations", "Catering", "About"];

export function SiteHeader() {
  const [open, setOpen] = useState(false);

  return (
    <header className="border-b border-gray-200">
      <div className="flex items-center justify-between ...">
        <p className="...">The Daily Grind</p>

        {/* The laptop nav: hidden on a phone, a row from md up. */}
        <nav className="hidden md:flex ...">...</nav>

        {/* The Menu button: only on a phone. */}
        <button type="button" className="md:hidden ..." onClick={() => setOpen(!open)}>
          {open ? "Close" : "Menu"}
        </button>
      </div>

      {/* The phone nav: a column, only when open, never from md up. */}
      {open && <nav className="flex flex-col ... md:hidden">...</nav>}
    </header>
  );
}

Two new utilities, and they're a pair. hidden is display: none, so hidden md:flex reads "not there on a phone, a flex row from 768px up." md:hidden is the opposite: "there on a phone, gone from 768px up." Between them, each screen size gets exactly one nav.

Expect this one. Open the menu at 375, then widen the window past 768 without closing it. If you left md:hidden off the phone nav, both navs show at once on a laptop. open is still true — the class is what keeps the phone nav off the big screen, whatever the state says.

9. The full check

Walk the whole page at 375, 768, and a full laptop width:

  • At 375: nothing side by side that doesn't fit, no word hanging out of its box, and the page can't be dragged sideways.
  • At exactly 768: the laptop layout switches on. This is the width where a missing or extra prefix shows up.
  • At laptop width: the page looks exactly like it did in step 1.

10. If there's time

  • Three feature cards across is tight on a tablet. Add a third tier: one on a phone, two from md, three from lg (1024px): grid-cols-1 md:grid-cols-2 lg:grid-cols-3.
  • Close the phone menu when a link in it is tapped — each link gets onClick={() => setOpen(false)}.
  • Make the header sticky top-0 bg-white so the Menu button is always within reach while scrolling on a phone.
  • Try it on your actual phone: run npm run dev, find your laptop's local IP address, and open http://that-address:3000 on the phone (same Wi-Fi).

AI hint — going deeper. Once it all works, ask:

"My Next.js page looks right in the browser's device toolbar at 375px. What's the viewport meta tag, why would a phone ignore my breakpoints without it, and does Next.js add it for me?"

What "done" looks like

  • At 375: features one per row, hours above location, hero text above a shorter photo, a full-width signup with the input above the button, a stacked footer, and a Menu button that opens and closes the links.
  • The page never scrolls sideways at 375.
  • At laptop width, nothing changed from where you started.
