Give the Button variants

The Daily Grind has one Button component, one look, used in four places. That's exactly what class ended with: duplication becomes a component. But look at the cart — Remove is the same solid green button as Add to cart. A button that deletes something shouldn't be visually identical to one that adds something. Tonight Button learns to look different on purpose, without turning back into four copy-pasted strings.

1. Run it, and look at Remove

npm install
npm run dev

Open http://localhost:3000, add a couple of drinks to the cart, and look at the Remove button next to each line. It's green, it's the same size as everything else, and nothing about it signals "this deletes something." Open components/Button.tsx — there's exactly one hardcoded look, used everywhere by every call site in components/ and app/.

2. The tempting fix, and why it doesn't work

Required — do this first, on purpose. The obvious way to make Remove red is a prop plugged straight into the class name:

export function Button({
  children,
  colour,
  onClick,
}: {
  children: React.ReactNode;
  colour: string;
  onClick?: () => void;
}) {
  return (
    <button
      type="button"
      className={`bg-${colour}-600 text-white px-4 py-2 rounded`}
      onClick={onClick}
    >
      {children}
    </button>
  );
}

Pass colour="red" to the Remove button's <Button> in components/CartItem.tsx, and colour="green" everywhere else it's used. Save, reload. Every single button loses its background — not just red, all of them, including the ones still asking for green.

Expect this one, and don't "fix" it by guessing. Tailwind doesn't run your code and doesn't know what colour will be when the page loads. At build time it reads every source file as plain text, looking for strings that are already complete class names. ` bg-${colour}-600` never appears anywhere in your files as the finished text bg-green-600 — only the unfinished template is there — so Tailwind never generates a rule for any colour built this way, correct-looking prop value or not.

3. The fix: a map of whole class names

Required. Instead of building a class name from the prop, use the prop to choose a class name that's already written out in full somewhere Tailwind can see it. A plain object works:

const colourStyles = {
  green: "bg-green-600 hover:bg-green-700",
  red: "bg-red-600 hover:bg-red-700",
};

export function Button({
  children,
  colour = "green",
  onClick,
}: {
  children: React.ReactNode;
  colour?: "green" | "red";
  onClick?: () => void;
}) {
  return (
    <button
      type="button"
      className={`${colourStyles[colour]} text-white px-4 py-2 rounded`}
      onClick={onClick}
    >
      {children}
    </button>
  );
}

Every value in colourStyles is a complete, literal string — bg-green-600, bg-red-600 — sitting right there in the file. Tailwind finds both of them scanning the text, generates a rule for both, and it's colourStyles[colour] that decides which one lands on the page at runtime. The colour is still dynamic. The class names never are.

colour = "green" as the default means every existing call site — Header, ProductCard, the cart and checkout pages — keeps working with no changes at all. Now go to components/CartItem.tsx and add colour="red" to the Remove button.

Stop and check. Remove should be red, and every other button on the site should still be the same green as before. If Remove is still green, double check the prop is actually being passed at that one call site — the default only applies where nothing is passed.

4. A second, independent variant: size

Required. Remove is red now, but it's still the same size as a primary "Add to cart" button, sitting right next to the total. Add a second prop, size, using the exact same map pattern — it doesn't touch colour at all, it just adds another independent choice: 

const sizeStyles = {
  sm: "text-sm px-2 py-1",
  md: "px-4 py-2",
  lg: "text-lg px-6 py-3",
};

Add size to the props (default it to "md"), and build the final className from both maps together: 

className={`${colourStyles[colour]} ${sizeStyles[size]} text-white rounded`}

Note that px-4 py-2 moved out of the hardcoded string and into sizeStyles.md — the old default padding is now just what "medium" means. Use size="sm" on Remove, and try size="lg" on Place order in app/checkout/page.tsx, since that's the button that actually finishes the purchase.

Stop and check. Four call sites, two independent props. Remove should now read as small, red, and clearly secondary. Place order should be the biggest button on the site. Everything else should be unchanged at the default green / md.

5. If there's time: a third dimension

  • Add an outline boolean prop. When true, swap the filled background for a border-only look — e.g. ` border-2 border-red-600 text-red-600` instead of bg-red-600 text-white. This is the same map idea again, just keyed by a boolean instead of a string.
  • Apply the same lookup-map pattern to a brand new, much smaller component — a Badge that takes a tone prop ("new" / "low-stock") and renders a small coloured pill. Same shape of problem, at a tenth the size.

AI hint — going deeper. Once colour and size both work, ask:

"I'm using a plain object to map a React prop to a set of complete Tailwind class strings, instead of building the class name with a template literal. What's this pattern usually called, and is there a small library that formalizes it for bigger component libraries?"

You don't need the library tonight — the object is the whole idea. It's worth knowing the pattern has a name before you go looking for it in a real codebase.

What "done" looks like

  • Button takes both a colour and a size prop, each backed by its own lookup object of complete class strings — no class name is ever built with a template literal from a prop.
  • Remove is small and red. Place order is large. Everything else defaults to the original green, medium look with no changes at its call site.
  • You can explain, without looking it up, why ` bg-${colour}-600` silently produces nothing and a lookup object doesn't.
