2. Before any code: what async/await actually is

Everything you've written so far in this class runs top to bottom, one line finishing before the next one starts. Asking a server for data breaks that. The request has to travel across the internet and come back, and that takes real time — milliseconds, sometimes seconds. Your code can't just freeze the whole browser tab while it waits.

fetch(url) doesn't hand you the data. It hands you a promise — a placeholder that says "I don't have your answer yet, but I will." await is what turns that placeholder back into a normal value your code can use, without you having to write nested callback code to wait for it: 

// Without await — a promise, chained
fetch(url).then((res) => res.json()).then((data) => {
  // data is finally here, three lines deep
});

// With await — reads top to bottom, like everything else you've written
const res = await fetch(url);
const data = await res.json();
// data is right here, same shape as always

Two things to notice in that second block. First, two awaits: fetch resolves once the server has answered at all, but turning that answer's body into usable JavaScript (res.json()) is also asynchronous, and needs its own await. Second: await only works inside a function marked async — it's the keyword that says "this function is allowed to pause partway through and pick back up later."

What "pause" does and doesn't mean. await pauses that function — it does not freeze the browser. The rest of the page stays clickable while your fetch is in flight. That's the whole reason a loading state matters: for however long the real pause takes, the screen has to say something, because the UI thread is still alive and the user can see it just sitting there.

4. Authorization: Bearer ... — what that header means

fetch sends no credentials unless you add them yourself. Headers go in a second argument: 

const res = await fetch(REVIEWS_URL, {
  headers: {
    Authorization: "Bearer mtc-fall-2026",
  },
});

Bearer <token> is a convention, not a law — it means "whoever holds this string is authorized," the same way holding a physical ticket gets you into a show without anyone checking your ID. It happens to be one of the most common ways real APIs ask for credentials, which is why it's worth knowing by name. Compare it with demo8's x-auth header: same idea, different header name, because the server's own documentation is the only thing that ever tells you which one a given API wants.

AI hint. If the difference between these header styles is still blurry, ask something concrete instead of "explain auth headers":

"What's the practical difference between a custom header like x-auth and the Authorization: Bearer convention? Are they enforced differently by browsers, or is it purely a server-side choice?"

5. Build the fetch, one situation at a time

Required. This is the same four-situation shape as demo7 and demo8 — you're applying a pattern you've already seen work, to a new URL and a new header.

  1. In ReviewList.tsx (or wherever you decide the fetch should live — see the callout below), replace the static sampleReviews import with a reviews state array that starts empty, loaded inside a useEffect that runs once.
  2. Write an async function that does the fetch: call it, then await it, using the header from step 4.
  3. fetch does not throw on a 404 or a 500 — it only throws if the network itself fails. Check res.ok yourself and throw when it's false, exactly like demo7 did for the menu.
  4. Wrap the whole thing in try/catch/finally: catch turns a thrown error into an error state message, finally turns off a loading state whether things worked or not.
  5. Render all four situations: loading, empty, here's the data, and error with a Try again button that re-runs the same function.

AI hint — deciding where the fetch logic goes. Demo7 and demo8 put the loading/error/menu state in page.tsx and passed it down as props. You could do that here, or keep it self-contained inside ReviewList. If you're not sure which fits better, that's a genuinely good question to bring to an assistant:

"I have a component that needs to fetch its own data with useEffect. Should the loading/error state live in that component, or in its parent and get passed down as props? What's the tradeoff?"

Either answer is defensible for a component this size. Knowing the tradeoff is the point, not landing on one specific answer.

Stop and check, in order.

  1. Plain load: reviews render, matching what sampleReviews used to show.
  2. ?delay=4000: you can actually see the loading state for four seconds.
  3. ?state=empty: a real sentence, not a blank section.
  4. ?state=error: an error message and a working Try again button.

Expect this one. Typo the token, or leave the header off entirely, and you'll get a 403 that looks identical to any other error — your error state can't tell "the server is down" from "you sent the wrong password." Open the Network tab (F12) and look at the actual response status and body when something doesn't work; don't guess from the UI alone.
