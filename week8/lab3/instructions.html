A login that survives the trip to the next page

Backspin Records now has a catalog, About, Help, and a page per record — lab 2, finished. There is no login anywhere. Tonight you add one, and make its answer to "who is this" available on every page, not just the one where they typed it in.

1. Run it

npm install
npm run dev

Open http://localhost:3000. Everything from lab 2 still works. Nothing knows who you are, because nothing has anywhere to keep that information.

2. Why a prop won't do this time

A component can hand a value to its own children as a prop. But app/login/page.tsx and app/account/page.tsx aren't parent and child — they're two different pages, and the only thing that contains both of them is layout.tsx, which can't hand custom props to {"{children}"}; it never even knows which page it's wrapping. That's exactly the wall demo2 hit with the cart. The fix is the same one: context — a value a whole section of the app can read without being handed it at every step.

3. Build the context

Required. Make app/UserContext.tsx with three pieces, the same shape as CartContext: a type for what's stored, the Context itself, and a UserProvider that owns the actual useState.

"use client";
import { createContext, useContext, useState } from "react";

type Shopper = { name: string; email: string };

type UserContextValue = {
  user: Shopper | null;
  login: (shopper: Shopper) => void;
  logout: () => void;
};

const UserContext = createContext<UserContextValue | null>(null);

export function UserProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<Shopper | null>(null);

  function login(shopper: Shopper) {
    setUser(shopper);
  }

  function logout() {
    setUser(null);
  }

  return (
    <UserContext.Provider value={{ user, login, logout }}>
      {children}
    </UserContext.Provider>
  );
}

export function useUser() {
  const value = useContext(UserContext);
  if (!value) throw new Error("useUser must be used inside a UserProvider");
  return value;
}

Wrap the app with it in app/layout.tsx, around both Header and {"{children}"} — Header needs to read it too, in step 5.

Stop and check. The app should still run exactly as before. A provider that nobody reads from yet changes nothing on screen — that's expected, not a sign you did it wrong.

4. Build the login page

Required. Make app/login/page.tsx: a name field, an email field, a submit button. No password, no validation beyond "don't submit empty fields" — this is a mock login, not a real one. On submit, call login() from your context with what was typed, then send them to /account:

"use client";
import { useState } from "react";
import { useRouter } from "next/navigation";
import { useUser } from "../UserContext";

export default function LoginPage() {
  const { login } = useUser();
  const router = useRouter();
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");

  function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    login({ name, email });
    router.push("/account");
  }

  // ...
}

5. Build the account page, and show who's logged in everywhere

Required. Make app/account/page.tsx. If user is null, show a message and a link to /login. Otherwise, show Welcome back, {"{"}user.name{"}"} and a Log out button that calls logout().

Then update components/Header.tsx to read the same context (it's already "use client" for the clock) and swap the nav's placeholder comment for a real link: Log in when user is null, the shopper's name linking to /account otherwise.

AI hint. If the account page and the header don't agree about who's logged in, a sharp question is:

"I have two components both reading the same React context. One shows the logged-in user and the other doesn't. What would cause that, given they're both inside the same provider?"

Nine times out of ten the answer is that one of them isn't actually inside the provider — check where in the tree each one sits.

6. Watch it survive a page — and not survive a refresh

Log in. Click to the catalog, to About, back to Account. The name should hold the whole way — that's context doing its job. Now hit a hard refresh.

You are logged out again, and that's correct. A refresh is the same event as the plain <a> from lab 1 — the whole app, clock included, gets thrown away and rebuilt from nothing. Context lives in memory, in the running app; it has nowhere to survive to.

7. Bonus — make it survive the refresh too

A cookie lives in the browser, not in the app's memory, so it survives the app being torn down. In login(), write the shopper to one: 

document.cookie = `mtc_user=${encodeURIComponent(JSON.stringify(shopper))}; path=/; max-age=604800`;

And in logout(), clear it the same way max-age=0 does. Then, in UserProvider, read it back once when the app starts:

useEffect(() => {
  const match = document.cookie.match(/(?:^|; )mtc_user=([^;]*)/);
  if (match) setUser(JSON.parse(decodeURIComponent(match[1])));
}, []);

Same reason as the clock. This has to be an effect, not straight in useState(...) — document doesn't exist while the server is rendering this component, only once it's running in the browser.

Refresh again. The name should hold this time — the cookie is doing what context alone couldn't.

What "done" looks like

  • Logging in on /login shows the shopper's name on /account and in the header, on every page.
  • A hard refresh logs them out again (or, with the bonus, doesn't).
  • Logging out clears the name from both the header and the account page.
