Give a record its own page

Backspin Records now has a catalog, an About page, and a Help Center — lab 1, finished. Every record title is already a link. Click one. You'll land on Next's default 404, because there is nowhere for it to go yet.

1. Run it, and see the crash

npm install
npm run dev

Open http://localhost:3000, click any record title. That 404 is today's whole assignment: build the page those links are already pointing at.

2. Make one dynamic page instead of six

Required. Make app/records/[id]/page.tsx. Square brackets mean "anything can go here, and I want to know what it was" — one file answers every /records/1 through /records/6, and anything else besides.

"use client";
import { useParams } from "next/navigation";
import { catalog } from "../../catalog";

export default function RecordPage() {
  const params = useParams();
  const id = params.id;
  // ...
}

Expect this one. catalog.find((a) => a.id === id) will fail for every record, even real ones. console.log(typeof id) and look closely — everything that arrives from the address bar is text, so "3" === 3 is false. Convert once, where it comes in:

const numericId = Number(params.id);
const album = catalog.find((a) => a.id === numericId);

3. Guard the address that doesn't exist

Required. Visit /records/9999. It crashes, because nothing considered the address being wrong. Add the guard:

import { notFound } from "next/navigation";

if (!album) notFound();

Show the album's title, artist, genre, year, price, and description. Mark it Out of stock somehow when inStock is false.

Stop and check. Click through all six records from the catalog. Then type /records/burrito in the address bar by hand. Both the missing-number case and the not-a-number case should show your not-found page, not a crash.

4. Bonus — ask a real server instead of the local array

There's a live class API behind a bearer token, same shape as the ones from week 6 and week 7: 

GET https://n8n.aseglave.net/webhook/mtc-records?id=3
Authorization: Bearer mtc-fall-2026

Swap the catalog.find(...) lookup for a useState + useEffect fetch against that URL, using numericId in the query string. Handle all three situations the same shape demo7/demo8 and week 6's lab3 used: loading, loaded, and a real error (this server answers a genuine 404 for an id it doesn't have — check res.ok yourself, fetch won't throw for you).

AI hint. If the fetch works from a REST client but not from the browser, a useful, specific prompt is:

"My fetch to an external API with an Authorization header works in curl but the browser console shows a CORS error. What's actually happening, and is this something the client can fix or does it have to be the server?"

5. Extra bonus — put the search in the address bar

Add a search box on the catalog page (app/page.tsx). Typing in it should filter the list and land in the URL as ?q=miles, using useSearchParams the same way demo1's menu filter did — so a search can be copied and sent to someone else, and survives a refresh. 

import { useSearchParams } from "next/navigation";

const searchParams = useSearchParams();
const q = searchParams.get("q") ?? "";

For the extra credit on top of that: instead of filtering the local catalog array, send q to the live API's own search: 

GET https://n8n.aseglave.net/webhook/mtc-records?q=miles
Authorization: Bearer mtc-fall-2026

You will hit this at npm run build, not npm run dev. useSearchParams needs a <Suspense> boundary around the part of the page that reads it, or the production build fails with a message about exactly that:

import { Suspense } from "react";

<Suspense fallback={<p>Loading…</p>}>
  <SearchableCatalog />
</Suspense>

What "done" looks like

  • Every record link from the catalog opens a real page with that record's details.
  • A bad id (/records/9999) or a non-numeric one (/records/burrito) shows a not-found page instead of crashing.
  • Bonus: the record page's data comes from the live API, with a real loading state and a real error state.
  • Extra bonus: a search box filters the catalog, lives in the URL, and (extra-extra) asks the live API's ?q= search instead of filtering locally.
