Paws & Whiskers: who are you, and is this yours?

A pet shelter's website. Anyone can see the pets waiting for a home. People who adopted one should be able to log in and see their own pet's private record. Tonight you add logins with Better Auth, straight from its own documentation, on a brand-new database. Then you make the API ask two questions before it hands over anything private: can you get in? and is this yours?

This lab is meant to stretch you. Every step tells you what to build and how to check it. If you get stuck, every step links to the full code for that step in the Code reference at the back. Try it yourself first, then look.

Better Auth is a library: code someone else wrote, that you install and use. On Tuesday we wrote logins by hand: hashing passwords, a sessions table, a cookie, expiry. Better Auth does all of that for us, more carefully. Part of tonight is learning to read its documentation, so several steps send you to the Better Auth website and tell you which part to read. Keep that tab open.

Why change sslmode? sslmode says how carefully the app checks it's really talking to Neon before sending the password. 5The secret and the address

In the docs, read Set Environment Variables. Better Auth needs two values in .env.local:

  • BETTER_AUTH_SECRET: a long random password that only your app knows. Better Auth uses it to sign each login cookie: it mixes the cookie's value with the secret and attaches the result, so if anyone changes the cookie, the signature stops matching and Better Auth refuses it.
  • BETTER_AUTH_URL: the address your app runs at. Better Auth uses it to refuse requests sent from other websites.

The docs page has a Generate Secret button, and suggests an openssl command, which Windows doesn't have. This works on every computer:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

Paste what it prints after BETTER_AUTH_SECRET=, and fill in the address:

BETTER_AUTH_SECRET=6f1c...a long line of letters and numbers...9e2b
BETTER_AUTH_URL=http://localhost:3000

Your secret is yours: don't paste it in Slack, in a screenshot, or into a prompt. A deployed app gets its own, different secret.

6lib/auth.ts

In the docs, read Create A Better Auth Instance, then Configure Database (click the postgres tab), then Authentication Methods. Together they say: make a file called auth.ts, give Better Auth a database, and turn on email and password.

Make a new folder lib next to app, and in it a file auth.ts. The docs make a brand-new Pool (a set of open connections to the database). We already have one in providers/neon/neonDatabaseProvider.ts, so Better Auth gets ours:

lib/auth.ts

import { betterAuth } from "better-auth";
import { NeonDatabaseProvider } from "../providers/neon/neonDatabaseProvider";

export const auth = betterAuth({
  database: NeonDatabaseProvider.getInstance().getPool(),
  emailAndPassword: { enabled: true },
});

That's the whole thing. Everything from Tuesday (hashing, sessions, the cookie, expiry, logging out) now lives behind those few lines.

Stuck? C1 has the file with comments.

You don't type these tables out. The docs give two commands: migrate makes the tables straight in your database; generate writes the SQL to a file so you can read it first and run it yourself. The red ERROR is Better Auth looking at your database and listing the four tables it doesn't have yet. That's exactly what the file it just wrote will fix. The last line is the one that matters.

8The route that answers /api/auth/...

In the docs, read Mount Handler and click the Next.js tab (the App Router one, not Pages Router). Better Auth answers a lot of addresses: /api/auth/sign-in/email, /api/auth/sign-up/email, /api/auth/sign-out, and more. You don't write a route for each. One file with a special name catches them all.

Make the folders app/api/auth/[...all]/ (yes, with the square brackets and the three dots) and in it route.ts, with the code from the docs:

app/api/auth/[...all]/route.ts

import { auth } from "@/lib/auth";
import { toNextJsHandler } from "better-auth/next-js";

export const { POST, GET } = toNextJsHandler(auth);

[...all] means "anything under here, however many slashes." @/lib/auth is a shortcut: @/ means "the top folder of this project," so you don't have to count ../. It's set up in tsconfig.json.

Start the app again (npm run dev).

Check it

Open localhost:3000/api/auth/get-session. It says null: Better Auth is answering, and nobody is logged in.

Now open localhost:3000/api/auth/ok. It says {"ok":true}. Did you ask for that address? Remember it for the next step.

9Close the doors you don't use

Tuesday's rule was deny by default: start with everything closed and open only what you need. Do it here:

  2. In lib/auth.ts, add the disabledPaths list from C1. That tells Better Auth itself to switch those addresses off too. It's a second lock behind the first: if somebody later loosens the list in route.ts, the riskiest ones stay shut.

12Can you get in? /api/my-pets

Logins work. But the API still doesn't ask who's calling. First, one file whose job is to answer "who is this?", the same job as Tuesday's authService. Make services/authService.ts (full file in C7). The part that matters:

const result = await auth.api.getSession({ headers: await headers() });

headers() (from "next/headers") is the request that just came in, cookie included. auth.api.getSession reads the cookie, checks its signature with your secret, looks the session up in the session table, and checks it hasn't expired. All four pass: you get the user back. Any one fails: null. Your method gives back { id, name, email }, or undefined when nobody is logged in.

Then open app/api/my-pets/route.ts and replace the TODOs:

  1. Ask AuthService.getInstance().getCurrentUser() who this is.
  2. Nobody? Answer { error: "Log in first" } with status 401.
  3. Somebody? Answer with PetService.getInstance().getPetsOwnedBy(user.email).

Where does "my" come from? From the session. Never from the request: there's no ?email= on the address for anyone to change to somebody else's.

Check it

13Is this yours? /api/my-pets/4

Now the open door from Step 3. Open app/api/my-pets/[id]/route.ts. It needs both questions, in this order:

  1. Can you get in? The same three lines as Step 12: no user, 401.

Why 5(a) is safe: "4 OR 1=1" isn't a whole number, so getPetRecord never even asks the database. Even if it did, the id goes in as $1, a value and never part of the SQL. That's Wednesday's Bobby Tables, closed twice.

16Break it with a fake cookie

Read the docs again, just below that code. There's a warning: getSessionCookie "only checks for the existence of a session cookie; it does not validate it." They mark that approach NOT SECURE.

Guess first: the proxy says "no cookie, no entry." What if I just make one up?

  3. Click My pets.

17The UserContext wrapper

So the page needs to know who you really are, checked against the database the way the API does it. And it isn't only this page: the header should say "Hi, Ana," the login page should say who's logged in. Every one of them asking separately would be a mess.

React context is made for this. You put a value into a wrapper high up, around the whole app, and any component inside can read it with useContext, without anyone passing it down by hand through every component in between.

Make app/UserContext.tsx from C11. It has three parts:

  • User: what we know about the person. id, name, email.
  • UserContext, made with createContext<User | null>(null). null means nobody is logged in.
  • UserProvider, the wrapper. It takes a user and puts it into the context for everything inside it.

Why a separate wrapper component? The layout is a server component: it runs on the server and can ask the database things. Context only works in the browser, in a client component (that's what "use client" at the top means). So the layout finds out who you are, and hands it to this small client component to share.

18The layout fills it in

Open app/layout.tsx and change it to C12. Three changes:

  1. export default async function RootLayout: it waits for an answer now.
  2. First line inside: const user = await AuthService.getInstance().getCurrentUser();. The same real check the API uses: cookie, signature, session table, expiry.
  3. Wrap everything inside <body> in <UserProvider user={user ?? null}>. (?? means "if it's undefined, use null instead.") The Log in link becomes {user ? "Hi, " + user.name : "Log in"}.

Check it

19The pages use it, and the proxy goes

app/my-pets/page.tsx (C13): get the user with const user = useContext(UserContext);. Only call the API when there is a user. When there isn't, show "This page is only for people who adopted a pet. Log in to see yours." and a link to /login. The heading can say whose pets these are, too.

app/login/page.tsx (C14): the top line comes from the context now, "Logged in as Ana Ortiz (ana@example.com)" or "Not logged in". After a successful log in, sign up or log out, call router.refresh() (from useRouter in "next/navigation").

Why router.refresh()? The layout found out who you are when the page loaded, before you clicked Log in. refresh() runs the layout again, so it asks again and the context, the header and this page all catch up. Forget it, and you log in and the page still says "Not logged in."

Now delete proxy.ts. The page doesn't need it any more, and a check that a fake cookie walks through isn't worth keeping.

Things that will bite you

  • SELECT * FROM user; gives back one row that says neondb_owner. user is a word Postgres already uses: it means "the database login running this query." Put the table name in double quotes: SELECT * FROM "user";. Same for Better Auth's camelCase columns: "userId", "expiresAt".
  • Restart after changing .env.local. Next only reads it when it starts.
  • Restart after adding a method to a service. The dev server keeps the copy of AuthService it already made, and the old copy doesn't have your new method: isVet is not a function. Stop it with Ctrl + C and npm run dev again.
  • A SECURITY WARNING about SSL modes every time the app starts: you skipped changing sslmode=require to sslmode=verify-full in Step 1. It still works; the warning is just noise.
  • Not found from /api/auth/... after Step 9: the address isn't on your list in route.ts. Check for a typo before adding anything.
  • Invalid origin when you log in: BETTER_AUTH_URL doesn't match the address in your browser. If Next said port 3001 because 3000 was taken, either stop the other app or change BETTER_AUTH_URL to http://localhost:3001 and restart.
  • Postman and /api/auth/...: Better Auth refuses a POST with no Origin header once there's a cookie (403 Missing or null Origin). Browsers always send one; Postman doesn't. Add a header Origin with the value http://localhost:3000. Our own /api/my-pets routes don't need it.
  • You logged in, and the page still says "Not logged in" (Part 4): router.refresh() is missing after the log in.
  • npx auth@latest generate can't connect: it reads NEON_DATABASE_URL from .env.local. Run it from the lab1 folder, and check the string.
  • Claude writes the tables by hand, uses Prisma or Drizzle, or puts getSession in every route. Remind it: Better Auth on a pg Pool, tables from npx auth@latest generate, and one AuthService that the routes ask.
  • The first npm run dev writes AGENTS.md. Notes from Next for AI coding tools. Leave it.

// /api/auth/... -- the addresses Better Auth answers.
// [...all] catches anything under /api/auth: /api/auth/sign-in/email,
// /api/auth/sign-up/email, /api/auth/sign-out, /api/auth/get-session...
import { toNextJsHandler } from "better-auth/next-js";
import { auth } from "@/lib/auth";

// The docs stop at this one line, which opens EVERY address Better Auth
// knows -- about thirty -- when our pages call four of them.
const betterAuth = toNextJsHandler(auth);

// Deny by default (Tuesday's rule): only the addresses we actually use.
// Anything else gets a 404 and never reaches Better Auth at all.
const allowed = {
  GET: ["/get-session"],
  POST: ["/sign-up/email", "/sign-in/email", "/sign-out"],
};

// "/api/auth/sign-in/email" -> "/sign-in/email"
function pathOf(request: Request) {
  return new URL(request.url).pathname.replace("/api/auth", "");
}

export async function GET(request: Request) {
  if (!allowed.GET.includes(pathOf(request))) {
    return new Response("Not found", { status: 404 });
  }
  return betterAuth.GET(request);
}

export async function POST(request: Request) {
  if (!allowed.POST.includes(pathOf(request))) {
    return new Response("Not found", { status: 404 });
  }
  return betterAuth.POST(request);
}

C7 · Who is this?

↑ back to Step 12

services/authService.ts

// The ONE file that knows who is logged in. Same job as Tuesday's.
// Routes ask this file "who is this?" and never read the cookie themselves.
import { headers } from "next/headers";
import { auth } from "../lib/auth";

export class AuthService {
  private static instance: AuthService;

  public static getInstance(): AuthService {
    if (!AuthService.instance) {
      AuthService.instance = new AuthService();
    }
    return AuthService.instance;
  }

  // Who sent this request? Better Auth reads the cookie, looks the session
  // up in the session table, and checks it hasn't expired.
  // Gives back undefined when nobody is logged in -- or when the cookie
  // is fake, expired, or for a session that was logged out.
  public async getCurrentUser() {
    const result = await auth.api.getSession({ headers: await headers() });
    if (!result) {
      return undefined;
    }
    return {
      id: result.user.id,
      name: result.user.name,
      email: result.user.email,
    };
  }
}

// GET /api/my-pets/4 -- one pet's full record: microchip, vet notes, owner.
// Private information, so two questions, in this order.
import { AuthService } from "../../../../services/authService";
import { PetService } from "../../../../services/petService";

export async function GET(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  // 1. Can you get in? Nobody logged in: 401.
  const user = await AuthService.getInstance().getCurrentUser();
  if (!user) {
    return Response.json({ error: "Log in first" }, { status: 401 });
  }

  const { id } = await params;
  const pet = await PetService.getInstance().getPetRecord(Number(id));

  // 2. Do you own this record? Logged in isn't enough. It has to be YOURS.
  // Someone else's pet gets the same 404 as a pet that doesn't exist,
  // so we don't even admit it's there.
  if (!pet || pet.ownerEmail !== user.email) {
    return Response.json({ error: `No pet of yours with id ${id}` }, { status: 404 });
  }
  return Response.json(pet);
}

// proxy.ts -- runs before every request to the addresses in config.matcher.
// No login cookie? Send them to the login page instead of /my-pets.
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";
import { getSessionCookie } from "better-auth/cookies";

export function proxy(request: NextRequest) {
  // This only checks that a cookie with the right NAME is there.
  // It never asks the database whether the session is real.
  if (!getSessionCookie(request)) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/my-pets"],
};

"use client";

// UserContext: who is logged in, handed to every page and component
// without passing it down as a prop through each one.
// The layout fills it in on the server, from Better Auth's real check.
import { createContext } from "react";

export type User = {
  id: string;
  name: string;
  email: string;
};

// null means nobody is logged in.
export const UserContext = createContext<User | null>(null);

// The wrapper. The layout is a server component, and server components
// can't hold a context, so this small client component does it for them.
export function UserProvider({
  user,
  children,
}: {
  user: User | null;
  children: React.ReactNode;
}) {
  return <UserContext value={user}>{children}</UserContext>;
}

// The ONE file that knows who is logged in. Same job as Tuesday's.

import { headers } from "next/headers";
import { auth } from "../lib/auth";
import { NeonDatabaseProvider } from "../providers/neon/neonDatabaseProvider";

export class AuthService {
  private static instance: AuthService;

  public static getInstance(): AuthService {
    if (!AuthService.instance) {
      AuthService.instance = new AuthService();
    }
    return AuthService.instance;
  }

  // Who sent this request? Better Auth reads the cookie, looks the session
  // up in the session table, and checks it hasn't expired.
  // Gives back undefined when nobody is logged in -- or when the cookie
  // is fake, expired, or for a session that was logged out.
  public async getCurrentUser() {
    const result = await auth.api.getSession({ headers: await headers() });
    if (!result) {
      return undefined;
    }
    return {
      id: result.user.id,
      name: result.user.name,
      email: result.user.email,
    };
  }

  // Is this person one of the shelter's vets? Better Auth has never heard
  // of vets. This is authorization, and it's ours: a row in our vets table.
  public async isVet(email: string) {
    const result = await NeonDatabaseProvider.getInstance()
      .getPool()
      .query("SELECT 1 FROM vets WHERE email = $1", [email]);
    return result.rows.length > 0;
  }
}

app/api/my-pets/[id]/route.ts

// GET /api/my-pets/4 -- one pet's full record: microchip, vet notes, owner.
// Private information, so two questions, in this order.
// Going further: a vet can see every pet's record, not just their own.
import { AuthService } from "../../../../services/authService";
import { PetService } from "../../../../services/petService";

export async function GET(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  // 1. Can you get in? Nobody logged in: 401.
  const user = await AuthService.getInstance().getCurrentUser();
  if (!user) {
    return Response.json({ error: "Log in first" }, { status: 401 });
  }

  const { id } = await params;
  const pet = await PetService.getInstance().getPetRecord(Number(id));
  if (!pet) {
    return Response.json({ error: `No pet of yours with id ${id}` }, { status: 404 });
  }

  // 2. Are you allowed this record? Yours, or you're a vet.
  // Ask the cheap question first: only check the vets table if it isn't yours.
  const isOwner = pet.ownerEmail === user.email;
  if (!isOwner && !(await AuthService.getInstance().isVet(user.email))) {
    return Response.json({ error: `No pet of yours with id ${id}` }, { status: 404 });
  }
  return Response.json(pet);
}
