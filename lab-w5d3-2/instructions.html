2. Move the stylesheet over

Expect this one. Tailwind quietly resets a lot of browser defaults — heading sizes, list bullets, paragraph margins. Our stylesheet sets all of that back on purpose, so the page should look right. But if something is mysteriously the wrong size and it isn't in styles.css, that's who did it. Inspect the element and look at what's crossed out.

While you're in there

Open src/app/layout.tsx and change the title and description in metadata to match this page. That export is the <title> tag — there is no <head> for you to edit, because there is no index.html any more. The <html> and <body> tags moved here, written once for the whole site.

3. Rebuild the page in JSX

Open index.html in a browser. Six vendors in a list, each with a name, what they sell, a stall number, and a little coloured pill saying whether they're here this Saturday. That's the target.

Same first move as lab 1: empty out src/app/page.tsx and rebuild the markup in JSX. class becomes className, every tag closes, HTML comments become {/* */}, and the whole thing has to come back from return wrapped in one parent element.

Stop here and check. The page at localhost:3000 should be indistinguishable from index.html — six rows, green pills on four of them, orange on two. Get that right before you refactor anything.

Expect this one. The page is full of curly quotes and dashes written as entities — &rsquo;, &mdash;, &ndash;. Those work fine in JSX text. What does not work is a bare apostrophe inside JSX in some setups, and a bare > anywhere. If the build complains about an unexpected token near a quote, that's what it is — use the entity.

4. The data goes in its own file

In lab 1 the words lived in the markup. That's fine for three cards that never change. Six vendors that change every week is a different story — that's data, and data belongs somewhere a person can edit without reading any JSX.

Required. Make src/types/vendor.ts. Three things go in it: a type for the status, a type for a vendor, and the array. 

// src/types/vendor.ts

// A vendor is either at the market this week or they are not.
// There is no third option, and TypeScript is going to enforce that.
export type VendorStatus = "here" | "away";

export type Vendor = {
  name: string;
  sells: string;
  stall: number;
  status: VendorStatus;
  backOn?: string; // only means anything when status is "away"
};

"here" | "away" is a union type. It is not string. It is a list of the only two strings allowed, and anything else is a compile error. backOn? with the question mark is an optional property — it can be missing entirely.

Then the data. Copy this in as-is:

export const vendors: Vendor[] = [
  { name: "Hollis Family Farm",     sells: "Tomatoes, squash, whatever came in Thursday", stall: 1,  status: "here" },
  { name: "Two Rivers Bread",       sells: "Sourdough, biscuits, the occasional cinnamon thing", stall: 3, status: "here" },
  { name: "Pike Creek Honey",       sells: "Wildflower and sourwood, pints and quarts", stall: 4,  status: "away", backOn: "Aug 9" },
  { name: "Marisol’s Salsas",      sells: "Six heats, from mild to why", stall: 7,  status: "here" },
  { name: "Gaffney Goat Dairy",     sells: "Chevre, feta, and soap nobody expects", stall: 8,  status: "away", backOn: "Aug 16" },
  { name: "Ledbetter Cut Flowers",  sells: "Zinnias and dahlias while they last", stall: 11, status: "here" },
];

Try to break it. Change one vendor's status to "maybe". Save. You should get a red underline immediately, and npm run build should fail, and the error should tell you the only two values it will accept. Put it back. That is a union type earning its keep — a typo that would have been a silently blank badge is now a build failure.

5. Three components, smallest first

Required. Build these in src/components/. Build them in this order — each one uses the one before it.

Pull the <header>, <nav> and <footer> out into their own components too, the way you did in lab 1. Those are the warm-up; the three above are the actual work.

Badge — deciding a class name in code

The badge is green when the vendor is here and orange when they're away. In the HTML you wrote that by hand — class="badge is-here" on some rows, class="badge is-away" on others. A component can't do that. It gets told the status and has to work out the class itself. 

// src/components/Badge.tsx

import type { VendorStatus } from "@/types/vendor";

type BadgeProps = {
  status: VendorStatus;
  backOn?: string;
};

export function Badge({ status, backOn }: BadgeProps) {
  const className = status === "here" ? "badge is-here" : "badge is-away";
  const label = status === "here" ? "Here" : `Back ${backOn}`;

  return <span className={className}>{label}</span>;
}

Two new things there. className={className} with curly braces instead of quotes — that's how you put a value into an attribute instead of a fixed string. And the backticks in `Back ${backOn}` are a template literal, same as in plain JavaScript.

Note import type, not plain import. You're importing a type, not a value — there's nothing there at runtime. TypeScript lets you say so, and saying so is the habit we want.

VendorList — the loop, and key

Six rows should not be six copies of anything. Hand the list component the whole array and let it produce a row per item: 

// src/components/VendorList.tsx

import type { Vendor } from "@/types/vendor";
import { VendorRow } from "@/components/VendorRow";

export function VendorList({ vendors }: { vendors: Vendor[] }) {
  return (
    <ul className="vendors">
      {vendors.map((vendor) => (
        <VendorRow key={vendor.name} vendor={vendor} />
      ))}
    </ul>
  );
}

It's .map(). The same .map() from the JavaScript weeks. It takes an array of objects and gives back an array of JSX elements, and React renders an array by rendering each thing in it.

Expect this one. Leave key off and the page renders perfectly — and the browser console fills up with "Each child in a list should have a unique key prop." Do that on purpose once. Read it. Then put key back.

key is how React tells the six rows apart between renders. It goes on the element .map() returns — not inside VendorRow, on the <VendorRow> tag itself. And it has to be genuinely unique. The array index is the tempting wrong answer; the vendor's name is the right one here.

import { Header } from "@/components/Header";

The real test. Add a seventh vendor to the array in vendor.ts. Save. Nothing else. A seventh row should appear, correctly styled, with the right coloured badge, and you should not have touched a single .tsx file to make it happen.

That is the thing worth learning tonight. Everything else is syntax.

6. Optional, if you finish early

  • Sort the list so the vendors who are here come first: [...vendors].sort(...) before you map. Copy the array first — .sort() changes the original in place, and mutating imported data is a bug waiting to happen.
  • Show a count in the <h2>: "Saturday's vendors — 4 of 6 here this week". Compute it with .filter(), don't type the number in. Then change a vendor's status and watch the heading follow.
  • backOn is optional, so `Back ${backOn}` will happily print Back undefined if somebody forgets it. Handle that — fall back to just "Away" when there's no date. Then ask yourself why TypeScript didn't stop you, and look up discriminated unions if you want the real answer.

What "done" looks like

  • The page at localhost:3000 is indistinguishable from index.html.
  • No vendor's name, stall number, or status appears anywhere in a .tsx file. It is all in src/types/vendor.ts.
  • VendorStatus is a union of exactly two strings, and setting a third one breaks the build.
  • VendorList uses .map() with a key, and the console has no warnings in it.
  • Adding a vendor to the array is a one-line change.
  • npm run build finishes with no errors.
